# UI / UX RULES — Mandatory for every screen and component

> Antigravity agent ku: Indha file-ah fully read pannu. Every frontend change ku munnaadi idha follow pannanum.
> Rule conflict irundha: **idha follow pannu, template instinct-ah illa.**
> Goal: Human designer panna maari, calm, professional student tool. "AI-generated template" maari irukkakoodaathu.

---

## 1. Design Philosophy

1. **Calm and focused.** Student exam stress la irukkaanga. UI shouldn't shout.
2. **One primary action per screen.** Today screen la "next best action" thaan hero.
3. **Content first, decoration last.** Ovvoru element ku oru reason irukkanum. Reason illa na remove.
4. **Honest and specific.** Real data, real labels, real numbers. Fake stats, fake testimonials, placeholder text kudaathu.
5. **Boring is good.** Predictable layouts, familiar patterns. Cleverness UX ku enemy.

---

## 2. Absolute BANS (never do these)

### 2.1 Emoji and icon abuse
- No emoji in headings, buttons, labels, nav, empty states, toasts, or marketing copy.
- No emoji as bullet points or as icons.
- Only exception: user-generated content (user types it themselves).
- Icons: **one icon library only** (lucide-react). Same stroke width, same size scale (16 / 20 / 24). No mixing sets.
- Icons support text; they do not replace labels (except universally known ones: close, search, menu).

### 2.2 AI references and AI-template look
- No "AI-powered", "Smart AI", "Powered by AI", "AI assistant", "Magic", "Supercharge", "Unlock", "Revolutionize", "Next-gen", "Seamless", "Elevate" in UI copy.
- No sparkle icons, robot icons, magic-wand icons, glowing orbs, or "brain" imagery.
- No "Generated by AI" badges as decoration.
- Where AI output needs user review (syllabus extraction), use plain functional wording:
  - Good: "Topics found in your syllabus. Review and edit before saving."
  - Bad: "AI magic extracted your topics!"
- The product speaks as a **tool**, not as a chatbot persona. No "Hi, I'm your AI buddy".
- No chat-bubble UI unless a real chat feature exists (it does not, in MVP).

### 2.3 Template visuals
- No purple-to-blue / pink-to-orange gradients as backgrounds, buttons, or text.
- No gradient text on headings.
- No glassmorphism (blurred translucent cards) as the default card style.
- No glowing shadows, neon borders, or animated gradient blobs.
- No floating 3D shapes, abstract blob backgrounds, or stock "dashboard mockup" hero images.
- No "three feature cards with icon + title + sentence" as the default section layout.
- No centered-everything layouts. Left-align text content; center only short hero/empty states.
- No giant rounded-3xl pill cards everywhere. Radius is consistent (see tokens).
- No decorative dividers, sparkles, confetti (except one subtle moment, see 9.3).

### 2.4 Copy and content
- No lorem ipsum, "Test", "Foo", "John Doe", "Acme Inc" in anything committed.
- No fake numbers ("10,000+ students"), fake reviews, fake logos.
- No exclamation-mark spam. Max one exclamation mark in the entire product, and only for genuine success.
- No marketing superlatives inside the app. The app is not a landing page.
- No "Welcome to the future of studying". Say what the screen does.

### 2.5 Interaction
- No auto-playing animations that loop.
- No modal on page load. No popups asking for notification permission on first visit.
- No dark patterns: no guilt-trip buttons ("No, I don't want to succeed"), no hidden cancel, no fake countdown timers.
- No infinite spinners without a timeout and an error state.

## 3. Design Tokens (single source of truth)

All styling comes from tokens in `tailwind.config` and CSS variables. **No hard-coded hex, px, or one-off shadows in components.**

### 3.1 Color

One neutral scale + one accent + semantic colors. That's all.

```text
Light mode
background        #FAFAF9
surface           #FFFFFF
surface-muted     #F5F5F4
border            #E7E5E4
text              #1C1917
text-muted        #57534E
text-subtle       #78716C
accent            #0F766E      (deep teal; primary buttons, links, focus)
accent-hover      #115E59
accent-soft       #CCFBF1      (subtle highlights only)
success           #15803D
warning           #B45309
danger            #B91C1C
```

```text
Dark mode (optional in MVP; if built, must pass same contrast rules)
background        #0C0A09
surface           #1C1917
surface-muted     #292524
border            #44403C
text              #FAFAF9
text-muted        #D6D3D1
text-subtle       #A8A29E
accent            #2DD4BF
```

Rules:
- Max **one accent color**. Semantic colors only for status, never decoration.
- Color is never the only signal. Pair with text or icon (e.g., "Overloaded" label, not just red).
- Contrast: body text **4.5:1** minimum, large text and UI borders **3:1**.
- Do not use pure black (#000) or pure white text on dark backgrounds.

### 3.2 Typography

- One font family: **Inter** (or Geist). One mono font only for code/numbers if needed.
- Scale (px / line-height): 12/16, 14/20, 16/24, 18/28, 20/28, 24/32, 30/36. Nothing outside the scale.
- Weights: 400 body, 500 labels/buttons, 600 headings. No 800/900. No thin weights.
- Body minimum **16px on mobile inputs** (prevents iOS zoom), 14px allowed for dense secondary text.
- Max line length for paragraphs: ~65 characters.
- Sentence case everywhere. No ALL CAPS except tiny labels (12px, letter-spaced) and sparingly.
- Numbers: use tabular-nums for scores, timers, tables.

### 3.3 Spacing and layout

- 4px base grid. Allowed spacing: 4, 8, 12, 16, 24, 32, 48, 64.
- Page padding: 16px mobile, 24px tablet, 32px desktop.
- Max content width: 1120px (app), 720px (reading/forms).
- Consistent vertical rhythm: same gap between sibling sections on every page.

### 3.4 Radius, borders, shadows

- Radius: **6px** (inputs, chips), **10px** (cards, buttons), **9999px** only for avatars and status dots.
- Borders: 1px `border` token. Prefer borders over shadows for separation.
- Shadows: at most one subtle shadow token for popovers/menus. Cards are flat with a border.

### 3.5 Motion

- Duration 120–200ms, ease-out. Only for state changes (hover, expand, toast in/out, page transitions subtle).
- Respect `prefers-reduced-motion`: disable non-essential motion.
- No parallax, no bouncing, no staggered "wow" entrances on lists.
- Skeleton loaders preferred over spinners for content areas.

## 4. Layout and Navigation

1. **Mobile-first.** Design at 360px first, then scale up. Test at 360, 768, 1024, 1440.
2. No horizontal scroll at any width.
3. Navigation:
   - Mobile: bottom tab bar, max 4 items (Today, Subjects, Exams, Settings).
   - Desktop: left sidebar or top bar, same 4 items.
   - Current page clearly indicated (not by color alone).
4. Home screen = **Today**. Not a dashboard with eight widgets.
5. Page structure: page title (H1) + one-line purpose (optional) + content. One H1 per page.
6. Primary action placement: consistent (top right on desktop, sticky bottom on mobile forms).
7. Touch targets: **minimum 44x44px**, with 8px minimum spacing between targets.
8. Breadcrumbs only when depth > 2.

## 5. Components

### 5.1 Buttons
- Hierarchy: **one primary** per view, secondary (outline), tertiary (text). Destructive uses danger color and requires confirmation.
- Labels are verbs and specific: "Save topics", "Add exam", "Delete account". Never "Submit", "OK", "Click here".
- Loading state: disabled + inline spinner + label changes ("Saving"). Prevent double submit.
- Same height scale: 36 / 40 / 44px.

### 5.2 Forms
- Label above input, always visible (no placeholder-as-label).
- Placeholder = example only, muted.
- Inline validation on blur, clear message under field: say what's wrong and how to fix.
  - Good: "Exam date must be today or later."
  - Bad: "Invalid input."
- Required fields marked in text ("Required"), optional fields marked "Optional". Don't rely on asterisks alone.
- Correct input types (`email`, `date`, `tel`) and `autocomplete` attributes. Use native date picker on mobile.
- Keyboard: Enter submits, Tab order logical, focus moves to first error on failed submit.
- Preserve user input on error. Never clear a form after a failed submit.
- Long forms split into steps with visible progress (onboarding).

### 5.3 Cards and lists
- Cards: flat, 1px border, 16px padding. No nested cards inside cards.
- Lists: consistent row height, clear primary text + secondary text, actions aligned right.
- Avoid cards for everything: use plain lists/tables where data is tabular.

### 5.4 Tables and data
- Right-align numbers, left-align text. Header row clearly distinct.
- On mobile, convert tables to stacked rows (not sideways scroll).
- Always show units (min, %, days).

### 5.5 Feedback
- Toasts: short, specific, auto-dismiss (4–6s), no emoji. "Topic rating saved."
- Errors: inline near the cause; page-level error only for page-level failures.
- Destructive actions: confirm dialog stating exactly what will be deleted. Offer undo where possible.
- Empty, loading, error, and success states are **mandatory** for every data view (see Section 7).

### 5.6 Charts and progress
- Use only when they add meaning (readiness over time, coverage). A number with a label beats a decorative chart.
- Axis labels, units, and text alternatives required. Don't use color alone to distinguish series.
- Progress bars show the number next to them.
- Readiness is always labelled **"Estimate"** with a short tooltip explaining what it's based on.

## 6. Product-specific UX Rules

1. **Today screen**
   - Top: one "Next action" card: what to do, how long, and **why** (1–3 plain reasons).
   - Below: remaining plan items (max 5), then upcoming exams (date + days left).
   - No greeting banners, no motivational quotes, no streak confetti.
2. **Every recommendation shows its reason.** Never show a recommendation without "why".
3. **Readiness** shows: percentage (estimate), coverage, weakest topics. No red/green shaming; use neutral language ("Needs review", not "You are failing").
4. **Syllabus extraction**
   - Show a progress state while processing, then an editable tree (rename, delete, add, reorder).
   - Banner: "Review the topics below before saving." Nothing is saved until the user confirms.
   - Let the user skip extraction and add topics manually.
5. **Topic rating**: three clear options (Strong / Okay / Weak) with plain labels, single tap, undoable.
6. **Onboarding**: max 4 steps, progress visible, skippable where possible, ends on Today with a real plan.
7. **Language**: English UI by default. If Tamil toggle is added, translate fully (no mixed half-translated screens) and test text overflow.
8. **Overload handling**: if workload > capacity, say so plainly and suggest what to defer. No alarmism.
9. **Delete account**: lives in Settings, requires typing a confirmation word, states what is erased.

## 7. Required States (every screen/component)

| State | Requirement |
|---|---|
| Loading | Skeleton matching final layout. No layout shift when data arrives. |
| Empty | One sentence explaining what belongs here + one clear action. No illustrations required. |
| Error | What failed, in plain words + Retry button. No stack traces, no "Something went wrong" alone. |
| Success | Brief confirmation near the action (toast or inline). |
| Offline | Clear banner when offline; queue or block actions with explanation. |
| Disabled | Visibly disabled + reason available (tooltip/helper text). |
| Long content | Text truncates with ellipsis or wraps; tested with 80-character subject names. |

Empty state example:
- Good: "No exams yet. Add an exam date to get a daily plan." + [Add exam]
- Bad: "Nothing here! Let's get started on your journey! 🚀"

## 8. Accessibility (non-negotiable)

- WCAG 2.2 AA target.
- All interactive elements keyboard reachable, visible focus ring (2px accent, 2px offset). Never `outline: none` without replacement.
- Semantic HTML first: `button`, `a`, `nav`, `main`, `label`, `ul/li`, headings in order. No clickable `div`.
- Every input has a programmatically associated label. Every icon-only button has `aria-label`.
- Images: meaningful alt text, or empty alt for decorative.
- Dialogs: focus trap, Escape closes, focus returns to trigger.
- Live regions for toasts and async status (`aria-live="polite"`).
- Support 200% zoom and text-size increase without breaking layout.
- Test with keyboard only and with a screen reader at least once per major flow.

## 9. Microcopy Style Guide

1. Plain, direct, short. Write like a clear teacher, not a marketer.
2. Say what happened and what to do next.
3. Use "you/your". Avoid "we" unless needed.
4. Consistent terms (pick one and keep it): **Subject, Exam, Topic, Task, Plan, Readiness, Revision**. Don't alternate with Course/Test/Chapter/To-do.
5. Buttons: verb + object. Titles: noun phrases. Errors: cause + fix.
6. Dates: unambiguous format ("24 Oct 2026"), relative where helpful ("in 5 days"). Time zone: IST.
7. Numbers: units always ("45 min", "72%").
8. No jokes in errors. No blame ("You entered wrong data").
9. One celebration moment allowed: first completed plan day, shown as a quiet inline message. No confetti, no emoji.

---

## 10. Responsive and Performance

- Breakpoints: 360 base, 640, 768, 1024, 1280.
- Images: `next/image`, correct sizes, lazy-load below the fold. Prefer no imagery in app screens.
- Fonts: `next/font`, subset, `display: swap`.
- Target: LCP < 2.5s on mid-range Android over 4G. Avoid layout shift (CLS < 0.1).
- Bundle: no heavy animation or chart libraries unless justified. Code-split routes.
- PWA: installable, offline shell, app icon without text clutter.

---

## 11. Code-level UI Rules

1. Use **shadcn/ui + Tailwind** components; customize through tokens, not per-component overrides.
2. Build shared primitives once (`Button`, `Input`, `Card`, `EmptyState`, `ErrorState`, `Skeleton`, `PageHeader`) and reuse. No duplicated one-off styles.
3. No inline styles, no arbitrary Tailwind values (`w-[317px]`, `text-[#123456]`) except documented exceptions.
4. Component props typed in TypeScript. No `any`.
5. Server data via TanStack Query with loading/error handled in one pattern.
6. No console logs, no commented-out code, no TODOs committed in UI files.
7. Strings centralized when Tamil support is planned (`lib/copy.ts`).
8. Each new screen: build mobile layout first, then tablet/desktop.

## 12. Review Checklist (agent must run before saying "phase done")

### Visual
- [ ] No emoji anywhere in UI copy or code strings
- [ ] No gradients, glow, glassmorphism, blobs
- [ ] No AI/magic/sparkle wording or icons
- [ ] Only tokens used (no stray hex/px)
- [ ] One accent color, one font, one icon set
- [ ] Spacing on the 4px scale; consistent radius

### Content
- [ ] No lorem ipsum, fake stats, fake testimonials
- [ ] Button labels are specific verbs
- [ ] Error messages state cause and fix
- [ ] Terminology consistent (Subject, Exam, Topic, Task, Plan, Readiness)
- [ ] Readiness labelled as an estimate; every recommendation has a reason

### Behavior
- [ ] Loading, empty, error, success states exist
- [ ] Forms validate inline, keep input on error, prevent double submit
- [ ] Destructive actions confirm
- [ ] Works at 360px with no horizontal scroll
- [ ] Touch targets >= 44px

### Accessibility
- [ ] Keyboard-only flow works, focus visible
- [ ] Labels, aria-labels, heading order correct
- [ ] Contrast checked (4.5:1 text, 3:1 UI)
- [ ] Reduced-motion respected

If any box fails, **fix it before reporting the phase as complete**, and list what you fixed.
